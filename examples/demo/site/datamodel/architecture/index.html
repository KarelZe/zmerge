Architecture¶

datamodel-code-generator is organized around one central idea: many input formats are normalized into a shared generation graph, then rendered through output-model-specific backends.

This page is partly generated from source code. The generated inventory is intentionally small so the narrative can stay hand-written while release-time details such as parser routes and output backends stay synchronized.

The CLI builds a Config from command-line arguments, pyproject.toml, and presets. It then calls the same generate() API that library users can call directly. generate() selects the parser, runs it, and either returns code or writes files. Model Processing Passes lists the passes inside Parser.parse().

Entry Points¶

The executable entry point is defined in pyproject.toml:

datamodel-codegen = "datamodel_code_generator.__main__:main"

src/datamodel_code_generator/__main__.py owns CLI-only behavior:

  • fast paths for --version, --help, prompt helpers, and JSON Schema output
  • argument parsing and shell completion
  • pyproject.toml profile loading and inheritance
  • --check diff generation
  • --watch regeneration
  • structured JSON command output
  • --input-model loading before normal generation

src/datamodel_code_generator/__init__.py owns the public generation API:

  • generate()
  • input type inference
  • raw JSON/YAML/CSV/Dict conversion through genson
  • MCP tool schema conversion
  • parser construction
  • generated headers and output file writing
  • optional model metadata emission

Parser Model¶

Each parser turns its input into DataModel objects. The parser-specific part is parse_raw(). The shared part is Parser.parse(), which handles sorting, module layout, imports, rendering, exports, formatting, and optional metadata.

flowchart TD
    parse["Parser.parse()"]
    raw["parse_raw()\nimplemented by subclasses"]
    sort["sort_data_models()"]
    modules["_build_module_structure()"]
    process["_process_single_module()"]
    render["_generate_module_output()"]
    metadata["_build_model_metadata()"]
    result["str or module map"]

    parse --> raw --> sort --> modules --> process --> render --> metadata --> result

JSON Schema is the main reusable parser surface. OpenAPI and AsyncAPI extend it. Avro, XML Schema, Protocol Buffers, raw data, and MCP tools convert to a JSON Schema-shaped document before using the same model-building machinery. GraphQL is the main parser that builds models directly from its own schema API.

Ordering and module splitting use small graph helpers. _scc.py finds strongly connected components with an iterative Tarjan traversal so large graphs do not hit Python recursion limits. parser/_graph.py provides stable topological ordering. Together they keep sort_data_models() deterministic and let _build_module_structure() move circular module SCCs into _internal.py forwarder modules when imports would otherwise cycle. The passes that read cycles or an order among models (module dependencies, class body order, circular root models, keep model order, alias cycles, nested model default factories) each take a snapshot of one reference graph, _reference_graph.py: the models by model key and the edges between them by kind, which answers their components and orders. The predicates that models answer on demand by walking base classes, root types or mapping defaults (inherited fields, ancestors, cyclic ancestry, the C3 order of bases, msgspec struct tags, pydantic protected namespaces, preservable root constraints, recursive dataclass mapping defaults) take a snapshot of the models they reach when asked and answer from it, each model once. Under the MODEL_GRAPH check, each answer is compared with the computation it replaced.

Intermediate Model Graph¶

The generation graph is built from a small set of core objects:

  • DataModel: a generated class, root model, type alias, enum, scalar alias, or union alias.
  • DataModelFieldBase: one field on a generated model, including defaults, aliases, constraints, and metadata.
  • DataType: a Python type annotation tree, including containers, unions, literals, generated-model references, and imports.
  • Reference: a schema reference path and generated Python name.
  • GenerationStore: the parser-owned model list plus a query index over model and type dependencies.
classDiagram

    Parser --> GenerationStore

    DataModel --> DataModelFieldBase

    DataModel --> Reference
    DataType --> Reference

GenerationStore is the preferred mutation boundary for parser-side changes that affect dependency facts. Parser code should register models and update references, fields, bases, names, and paths through store methods instead of mutating the live objects directly. GenerationIndex keeps stable facts about the model list and gives later phases efficient queries such as "which data types point at this reference?". A refresh records only the models that were appended or that store mutations changed, and rebuilds every fact only when the model list changes otherwise or discard_derived_facts() drops them.

Model Processing Passes¶

Parser.parse() runs a fixed sequence of passes between parse_raw() and rendering. Most of them change models, fields and data types in place, so a fact that one pass reads may still be changed by a later pass. This section lists the passes in execution order, says when each fact becomes final, and shows where a new decision belongs. Paths are relative to src/datamodel_code_generator/; names are given as file:function so they can be found with git grep.

Layers¶

__init__.py:_parse_generation may run L0–L8 again with a fresh parser (root-model collapse that stops before a data type cycle, yielding names that class-keyed options name, untyped nullable maps, invalid dotted stdout modules). These are retries around the whole pipeline, not passes inside it.

L0. _load_source_dict calls _read_document, which keeps the document as written and, under --use-single-value-enum-as-const, rewrites one-value enum to const copy-on-write, except beside nullable: true when the value is not null (_single_value_enum_as_const, which skips instance-data keywords and extension keys other than x-propertyNames through _document_child_entries). _parse_file then calls _prepare_schema_resources, which adds the document to the schema graph (parser/_schema_graph.py): walk_schema_resources finds which absolute URI names which schema of it (the root, $id or draft-04 id resources, the implicit component resources of OpenAPI, $anchor and $dynamicAnchor) and returns one frozen DocumentResources record, from which ResourceRegistry.register fills the registry dicts L1 resolves references through; then $refs that resolve through an embedded $id are rewritten copy-on-write (_rewrite_schema_resource_refs), each $ref and $dynamicRef keyword becomes a ResolvedRef (a str equal to the value, carrying its RefEdge: the holder's location and document; SchemaGraphBuilder.with_ref_edges, copy-on-write, only at the keywords that hold schemas, never inside instance data, examples, extensions, OAuth scopes, discriminator mappings or unknown keywords; JsonSchemaObject and the OpenAPI ReferenceObject keep the edge through a wrap validator), and the location of every object of the prepared document is indexed (SchemaGraphBuilder.index_document, see Metadata Output). Referenced documents go through the same steps when resolve_ref loads them: documents enter the graph in the order L1 asks for them, and the graph never loads one by itself. With DATAMODEL_CODE_GENERATOR_CHECK_SCHEMA_GRAPH=1, which tests/conftest.py sets for the test suite, each registration is compared with the registry that the walk the graph replaced (_register_schema_resources) leaves for the same document, and each edge with its resolution at the sites: the key get_ref_data_type and resolve_ref would compute in their own context equals the edge's key, unless that context raises or names no value of a loaded document (a reference resolved outside its own document, recorded as fixed-context), and the object _load_ref_schema_object, get_ref_model, _resolve_asyncapi_ref and the api scope load is the registered target the edge names, except a pointer the parser splits at another / and references of documents that resolve references against themselves (_resolve_lenient_resource_ref). Every reference whose target is static carries an edge: a rewrite of a reference to name its target (rebased, canonicalized, lenient or normalized) keeps it (keep_resolved_ref); an object a reference names is read as a schema once (SchemaGraphBuilder.read_as_schema), so a $ref the walk read as data or names there (a nested definitions container) gets one too; schemas converted from another format are mounted with edges to the locations their targets are mounted at (an AsyncAPI payload converted from Protocol Buffers or XML Schema under the internal container of a root the graph owns for its document, SchemaGraphBuilder.mount_root and mount_in, so the loaded document is never written); and a reference the parser derives gets the edge of the reference it stands for, with its RefOrigin (_derived_ref: discriminator mappings and subtypes, x-python-type names, a merged $recursiveRef with a fixed target, an itemSchema projection, an AsyncAPI Reference Object). Only the references of the dynamic-scope rule (_dynamic_scope_target: a $recursiveRef, and a plain-name $dynamicRef bound in the dynamic scope or named by the first $dynamicAnchor of its name in the document being parsed) stay plain strings: they resolve against the dynamic scope of the model being parsed, not their own document. With report:<path>, one line per site and origin counts the references that reached it with their edge and as plain strings. Every L1 site takes the key of a reference from its edge (_ref_key, _ref_path): the edge's spelling resolved once, at its first consumption, in the document that holds it (_home_context: its location, root $id and, for an OpenAPI input document or under the api scope, its $self; a schema the parser keeps in a document of its own, an Avro schema of an AsyncAPI document, names that document as its edges' home) through the external mapping, the embedded resource, the normalized spelling and ModelResolver.resolve_ref; a new model is named after that spelling (ModelResolver._add_ref_at). A plain string has no edge and resolves in the context its caller set. OpenAPI and AsyncAPI register a schema that declares a discriminator, and a component schema whose allOf names one, under the key of the reference that names the schema from its own document (_schema_key), the key the references to it get, whatever document is being parsed when the discriminators are collected. A JSON object of a loaded document is validated once per parse (SchemaGraphBuilder.schema): the targets _load_ref_schema_object, _load_inherited_schema_object and OpenAPI's resolve_object load, the response and request body targets of get_ref_model, and the if, then, else and not branches _get_conditional_schema reads share one object per located value and its type, which no reader writes; the schema graph check compares each shared object at the end of L1 with the fingerprint taken when it was validated (kind="shared-schema"). The walks that follow references from a schema (field flags, literal and null checks, inherited properties and overrides, validation sources, uniqueItems rules, merged allOf values) visit each schema graph node once (SchemaNodeId, the location of the object a reference names: _key_node), and a $ref target merged with its sibling keywords is dumped once per node and document being parsed (_ref_target_dump). A local reference whose model a document has not parsed yet is reserved for that document (reserved_refs). _parse_file, _resolve_unparsed_json_pointer and AsyncAPI's _resolve_asyncapi_unparsed_json_pointer take the targets from one worklist (_reserved_targets: a ReservedTarget with the document, the key and the node the key names in the document's prepared tree), in key order, repeating while a round reserves more keys (_parse_file) or adds models (the others), and parse each target from the prepared tree; the schema graph check loads the source again and compares the value at each target (kind="reserved-target"). walk_schema_resources also keeps the anchor tables of each document: its $dynamicAnchor names (the first in walk order wins) and its $recursiveAnchor: true schemas (ResourceRegistry.anchor_tables). The $dynamicRef analysis (_dynamic_anchors_used, _dynamic_ref_edges) and the models specialized for a dynamic scope are keyed by the schema graph node a reference names, so references that spell one schema differently share its analysis and its specialized model. The fallbacks of the dynamic-scope rule still read the anchors L1 has registered so far (_build_anchor_indexes and _parse_file: the root, the definitions and each schema parsed through _parse_raw_or_validated_obj): _resolve_dynamic_ref, _resolve_recursive_ref and _recursive_ref_target. The schema graph check compares each of their answers with the one of the document's anchor tables and records a difference (kind="anchor-answer"): a $recursiveAnchor below properties is never registered, and an OpenAPI component's $dynamicRef parsed before the component that declares its anchor resolves through its edge instead. OpenAPI parses its main document in _parse_specification (merging path-level parameters into shallow copies of operations in _process_path_items) instead of _parse_file. Converted inputs (Avro, XML Schema, Protocol Buffers) build a JSON Schema dict and call _parse_file without _read_document, so document rewrites do not apply to them.

L1. Each place where the parser meets a schema object chooses its parse method from one table of parser/_schema_dispatch.py (Position): DEFINITION in _parse_schema_obj (definitions, roots, reserved targets, AsyncAPI payloads and the api scope), FIELD in parse_item (fields, items and map values) and OPENAPI_OPERATION in OpenAPIParser.parse_schema (the bodies, responses and parameters of the legacy scopes). A table holds, in order, the steps that rewrite the site (a $ref with sibling keywords merged with its target, _merge_ref_with_schema) and the rows whose predicates choose parse_array, parse_all_of, parse_one_of or parse_any_of (both through parse_combined_schema), parse_object, parse_enum, parse_root_type and the other builders; the rows of an object-kind schema (_OBJECT_KIND_ROWS) are shared by the definition table and _parse_object_kind_schema. Rows call the public hooks through the parser, so overriding subclasses keep working; a change of what a position parses is a row edit. _choose returns the chosen row and the position's method builds it in its own frame, so a nested schema costs no more stack frames per level than the parse methods it reaches (test_main_nesting_within_recursion_limit fails when it does). The schema graph check also asks the dispatch each table replaced (_legacy_*_path) and reports a schema for which it takes other entries (kind="dispatch"). That merge, the inherited $ref property merge (_resolve_inherited_parent_property) and a property that overrides an inherited one (_merge_properties_with_parent_constraints, unless --allof-merge-mode none) stand for the intersection of their parts: the earlier merge (_deep_merge, _merge_property_schemas) stays wherever it enforces what the intersection enforces, and parser/_intersection.py:intersect_keywords writes the tightest bounds, the least common multipleOf, the common type and enum values, the union of required and a false that a part sets where the merge does not; nested schemas follow the same rule. Where the document's dialect (draft 7 or earlier, OpenAPI 3.0) does not read $ref siblings as parts, a sibling enum that the document writes does not narrow the referenced schema (the legacy sibling enum row; an inherited property override is a part in every dialect). Null comes from the site's own nullable, type list or null value, else only if every part admits it. A keyword whose parts have no value in common keeps the earlier value and warns (warn_unsatisfiable); pattern, format, tuple positions, combinators and allOf members are not intersected there yet. A oneOf/anyOf of constants can become a synthetic enum (_extract_const_enum_from_combined). An enum class takes a value base (IntEnum, StrEnum, --use-subclass-enum's (T, Enum)) only when that base keeps every member value (T(v) == v, NaN equal to itself), and is a plain Enum otherwise (model/_decisions/enum_kind.py:decide_enum_kind). A const that admits some but not all values of the enum beside it leaves every enum class as written; parse_enum records the const for the model it builds (_note_const_narrowing), the end of L1 marks every value that names that model, and L5 __type_const_narrowed_values types those values. A Literal enum route (_enum_value_type), a propertyNames key and a Literal root type keep only the admitted values (_const_narrowed_enum); a const equal to none of the values only warns. Under --read-const-beside-enum and --use-single-value-enum-as-const each enum route reads an enum that admits the const beside it as that const, without an enum class (_reads_enum_as_const); like the L0 rewrite, it keeps an enum beside nullable: true and a const other than null, and a model built for the schema object itself then holds only the admitted values (_definition_enum). An object map, an object without properties whose keys and values patternProperties, propertyNames or additionalProperties type, is built by one builder at every position (_parse_object_map): one dict whose value type is the union of the value types of its key classes, never a union of dicts. The dict itself admits the null of a type array of object and null, or of nullable: true under --strict-nullable as _get_data_type does for other types, so property counts stay on it, and the other types of a type array join it in a union. A nullable that parse_combined_schema copies from an anyOf or oneOf parent into a branch is marked on the branch, and the dict of that branch leaves it to the union. Names come from ModelResolver.add. Each model records the location of the schema object it is built from on its Reference (_record_schema_object). Every use of a reference gets a new DataType that points to the one shared Reference. allOf $ref items become base classes; inherited fields whose parent is not parsed yet stay as placeholders that L5 resolves. Discriminators are only captured here (field.extras["discriminator"]). Field construction already decides const handling: DataModelFieldBase.__init__ calls process_const(), which types the const and decides its default and nullability (model/_decisions/literal_default.py). Dataclass-like models (dataclasses, Pydantic dataclasses, msgspec Structs) sort their fields when they are built, by DataModel.FIELD_CONSTRUCTION_ORDER_KEY. The key reads only facts known then: on a Pydantic dataclass, a None default that --strip-default-none may keep counts as no default, while a msgspec Struct counts every optional field as having one, as it never strips its defaults. __fix_constructor_field_ordering, after the decision phase, decides with the output model's assignment facts (DataModel._field_assignment_facts, the row FIELD_ASSIGNMENT_CHECKER is a view of), which state what the template writes, and moves fields whose default the template keeps after the fields without one.

Pass Declarations¶

Every pass is declared in parser/_pass_decls.py as a PassDecl: its name, phase, scope (once over every model, or once per output module over that module's models), kind (transform, plan, repair, check, setup, bookkeeping), the Fact and RenderFact members of parser/_facts.py it reads and writes, explicit order edges (after), the change that removes a repair (removed_by) and the phase it moves to (target). scripts/check_fact_finality.py (run by the test suite) checks that names are unique, phases never go back in execution order, a repair names what removes it, and setup, check and bookkeeping passes write no fact (a check pass may write the pseudo-fact STDERR, the warnings it emits, so that two passes that warn are ordered).

Parser.parse() runs the passes from class-level tables in parser/base.py (Parser.__PIPELINE, with the bodies of the overridable hooks _build_module_structure, _process_single_module and _finalize_modules), built from the steps of parser/_pipeline.py: a PassSpec runs one declared pass, when its condition holds; a ForEachModule runs passes module by module; a HookCall calls an overridable method whose default runs a sub-table; a Segment enters a phase on the store (GenerationStore.enter_phase, read as GenerationStore.phase) and the boundary before it (PARSED, B1, DECIDED, B2), then runs its steps. The Runner is the only caller of a pass, inside fact_pass(DECL) (parser/_finality.py) with the models the finality check compares; steps call passes through the parser instance, so overrides and --debug tracing apply as to any method. The two diagnostics warnings that name the code calling parse() find that frame however deep the pipeline is (stacklevel_at_parse_caller).

The order rule (parser/_pipeline.py:check_order): two passes of one segment conflict when one writes what the other reads or both write the same fact. Where only the earlier writes what the later reads, a derived edge orders them; every other conflicting pair needs explicit after edges, with their reasons, that connect it directly or through other edges. An explicit edge replaces the derived edge of its pair; one that runs a reader before a writer of what it reads is a provisional read, listed below the table. scripts/check_pass_pipeline.py (run by the test suite) checks that the tables run every declaration once in PASS_DECLS order, in the phase of its segment and with its scope, that the segments enter the boundaries in order and satisfy the order rule, that the repair set only shrinks, that every decision registry follows the rules of the Decision Phase, that only GenerationStore.seal_facts builds FinalFacts, that no code outside Parser reaches its name-mangled members, and lists the warnings whose stacklevel reaches past their caller. A pass trace (scripts/check_pass_pipeline.py --trace) records each pass that runs; the test suite keeps the traces of a few inputs and checks that some input runs every declared pass. The finality check (Fact Finality) compares the writes of fact rows with the declarations while the generator runs; reads and the writes of presentation rows are declared from the code. A new pass gets a declaration and a table entry.

Decision Phase¶

The decide segment (DECIDE, entered at B1 right after __apply_generic_base_class) runs the decisions of the parser's registry, Parser._DECISION_PASSES (parser/_phases.py). The registry holds one decision, omit_held_null (parser/_held_null.py, --omit-redundant-reference-null, #5081): a type that names a model holding null itself (a root model or type alias whose type admits None, or an enum with a None member) drops the None it restates of that model; the None it writes itself stays. A decision is a DecisionPass: a DecisionSpec (its PassDecl, a global transform of DECIDE that reads and writes Fact members only, and the issue it fixes), the writer protocol of its writes (a DecisionWriter), run(facts, writer) and, for a decision behind an option, when(parser). When a decision runs, GenerationStore.seal_facts builds the one FinalFacts of the parse: per output module, the models that render (unused models, which leave their modules later, are left out), as the read-only views of model/_views.py (ModelView, FieldView, DataTypeView, ReferenceView). The views list the facts final at B1 and rendered nullability through admits_none, never the is_optional that render preparation writes; presentation attributes are not part of them, and type checking rejects writes through a view. Every decision writes through _DecisionWriter, the one implementation of the writer protocols over the store, which records the models it changes (DecisionOutcome). A writer never changes a data type node that other fields share: it replaces the node in the one field with a copy first.

The decisions run in the order the order rule computes from their declarations (decision_order): a decision that reads what another writes runs after it, every other conflicting pair needs an After edge in decl.after (the only explicit edges a decision has), and the registration order breaks ties. Each runs inside fact_pass with its declaration, so the finality check holds its writes to the facts it declares. With the finality check on, FinalFacts holds guarded views that report each read of a render fact as render-read (Fact Finality). scripts/check_pass_pipeline.py checks every registry: unique names that no table pass has, global transforms of DECIDE that read and write facts only, an issue each, writer protocols that _DecisionWriter implements, and the order rule.

Hidden Couplings¶

Per-module passes that change models in other modules. L5 receives only the current module's models, but reaches other modules through references. A model in another module may already be processed (its ordering, defaults and quoting are done) or not yet (its overrides, collapse and reuse have not run).

Nodes with more than one holder. A DataType normally has one owner (parent). These create more holders, and an in-place write to such a node changes every holder:

  • Same-module root-model collapse inlines root_type_field.data_type.model_copy(), a shallow copy that shares the root type's data_types list and dict_key with the root model and with every other site that inlined it. Cross-module collapse uses _copy_data_type, a tree copy. The shared members keep parent in the root model's tree, so a later collapse that replaces one (replace_nested_data_type, then set_nested_data_types on that parent) rebinds only the root model's list and detaches the old member, which the other holders still contain.
  • _create_set_from_list returns a model_copy() that shares its members with the list node, and for nested lists the store's swap_data_type rebinds the parent's data_types to a new list.
  • __apply_generic_base_class puts one BaseClassDataType object into the base list of every target model.
  • __extract_inherited_enum builds the merged Enum from the base enums' field objects and gives it the original model's Reference.
  • Reuse, collapse-reuse redirects and Reference objects are shared by design: a rename or an edit of a canonical model is seen by every user.

Known in-place writers on such nodes: forward-reference quoting in __update_type_aliases, model-level type overrides (_apply_override_to_data_type), import aliases (__change_from_import and the L6 import repairs), and root-model collapse replacing a member of a shared list.

In practice, the fields, types, defaults, tags and bases of every model are final once __apply_generic_base_class has run in _finalize_modules, except pydantic v2 type-alias bodies (__prepare_type_alias_fields). Models that collapse left unused stay in the module lists until unused-model removal, so a pass placed there skips unused_models. Removal finds a model through the module index built before L3 merges import cycles, so it does not reach a merged _internal module, except for a root model that the parent strategy replaced by its inner model, which is removed from the module that holds it: unused roots of other collapses stay in merged modules. Later passes change presentation or derive from those facts.

The finality check (parser/_finality.py, DATAMODEL_CODE_GENERATOR_CHECK_FACT_FINALITY, on in every test) checks this table and the pass declarations while the generator runs. It keeps a fingerprint per model: the values of the fact rows of parser/_facts.py on the model, its fields and the data types of their types and of its bases, holding the objects it keys. When a pass ends, it compares the models the pass touched (the models of its module and the models they reference, for a module pass; the models that guarded writes and store operations reached; the models the pass reported changed with GenerationStore.note_changed_models or a field's invalidate_semantic_caches) and reports a changed row as

  • undeclared when the pass declares none of the row's facts,
  • other-module when a module pass changed a model of another module (whether that module is done is in the report),
  • frozen when every declared fact of the row is final at a freeze point the pipeline has passed: B1 (entering DECIDE, right after __apply_generic_base_class) for facts, B2 (entering IMPORTS) for the rendered nullability rows and the render facts that RENDER_FACT_FREEZE_POINTS freezes there,
  • after-final when the phase is later than the row's final_after; a decision writes the facts it declares until DECIDE ends, whatever the row's final_after.

A change that no pass covers is unattributed, found at the next comparison of its model: when a pass touches it, when the next pass starts (for a guarded write outside every pass), at the start and the end of each module and when the pipeline leaves a phase: entering a phase (GenerationStore.enter_phase, which includes B1 and B2) compares every model. With DATAMODEL_CODE_GENERATOR_CHECK_FACT_FINALITY_SWEEP on as well (the test suite on the newest Python), a global pass that transforms or repairs compares every model too. A pass that runs in another phase than it declares is wrong-phase. At B2 the ordering-input check compares the fields of bases that constructor ordering read after the decision phase (__get_inherited_constructor_info), with the facts fix_constructor_field_ordering declares as reads, with those fields at B2 (ordering-input): render preparation of a later module must not change what an earlier module's ordering read. KNOWN_WRITES in parser/_finality.py lists the violations of today's pipeline, each with the roadmap item that removes it and a witness, the datamodel-codegen arguments of one run that makes it; they are reported with report:<path> and never raise. python scripts/check_fact_finality.py --witnesses (and the test suite) run the witnesses and report the entries whose witness no longer makes them, so the list only shrinks. Presentation rows, parser state, module imports and computed rows (a property of the model class) are not fingerprinted, and only type aliases hold TYPE_ALIAS_BODY in their rows. A row is judged by the freeze points of the facts the pass declares, so a pass that declares only IMPORT_ALIASES (final at render) can change DataType.type, python_type, kwargs or extras after B1 without a report, and one that declares only TYPE_ALIAS_BODY (final at B2) can change a type alias's data_type or data_types after B1, although FIELD_TYPES of those rows is final at B1. A decision of the decision phase reads FinalFacts through guarded views: reading a render fact, an attribute (or a key of extras or __dict__) whose row holds facts none of which is a Fact final at B1, is render-read, named after the running decision. The views give the graph objects they reach as views and their lists as tuples, and see only what a decision reads on them, not what the methods and properties of the classes read inside.

The check also seals the graph at the freeze points: once the pipeline has passed B1, each guarded write to an object that a fingerprint holds (an attribute assignment of a fact or presentation row, or a mutation of a guarded list such as fields, base_classes or data_types) is judged when it is made, inside store operations as well, with the same frozen rule: the facts the running pass declares among the row's facts, or all of the row's facts outside every pass. A write that changes no value is not judged, and it covers presentation rows, which no fingerprint holds.

Generation Store¶

GenerationStore (parser/generation.py) owns Parser.results and indexes, per model, its reference and paths and, per DataType occurrence, its owner model, field index and role (field, base, nested, dict key). It also records DataType objects that occur in more than one place (shared_data_type_fact_ids), models by path and by model key, and every reference occurrence of a type tree as a site (parser/_sites.py:RefSite): its owner model, field, position in the tree, node, target model key, kind (type, base, alias_body) and provenance, keyed by the id of its occurrence and listed per target (sites_by_target). Queries refresh the facts when a mutation marked them dirty, either incrementally for appended and changed models or with a full rebuild. Every store mutation states what it does to the sites (SITE_EFFECTS, NO_SITE_EFFECT): a new site takes the provenance of the mutation that made it (redirected with the model it named before and the site at its place, collapsed with the root model and its site, overridden, copied), the sites of the parsed models are parsed, and a site whose occurrence a refresh keeps keeps its provenance; renames touch no site, since sites store no names.

Every mutation goes through the store's GraphBuilder, the capability that GenerationStore.builder() returns (Parser._graph_builder in the parser): one method per mutation of GENERATION_STORE_MUTATION_METHODS, each calling the store's operation of the same name, so that a store subclass that overrides an operation and the debug checks that wrap the operations on the store keep seeing every call. The operations on GenerationStore itself are deprecated for every other caller (@deprecated(category=None): ty lists the callers, and no warning is raised at run time).

A Reference takes a ModelKey when it is built: Reference.model_post_init stores the next value of a process-wide counter in its __dict__, beside its schema location, and parser/_graph_ids.py:model_key_of reads it (identity_of returns the ModelIdentity record: the key, the schema location and the owner). The owner (owner_of) is the model whose builder built this one: each model builder of JsonSchemaParser runs in a frame whose cell takes the model it built when it returns, and a model records the frames open when it is recorded. A read or write variant stands for its base model in those frames, so it takes the base's owner; a document parse (_parse_file, also for a $ref target) starts with no frame open, so its models are roots. The store keys model_by_ref_id, sites_by_target and the reference counts of root collapse by it, through GenerationStore.model_key, instead of id(reference), which Python reuses once a Reference is freed. Copies of a Reference (deepcopy, model_copy, pickling) keep the key of their original, so the store would take a copy for the model it was copied from. DATAMODEL_CODE_GENERATOR_CHECK_MODEL_GRAPH reports a Reference object that the store records or is asked about when another one took its key first, and, at the end of L1, a model parsed from a JSON document that has no owner and is not a root. Because the key sits in __dict__, two distinct References with equal fields compare unequal under pydantic before 2.6, whose == compares __dict__; no parser comparison depends on that (GR5 turns the remaining == sites into is). Other parser maps still identify models by path, class name or id().

The store owns the parse's memos (_parse_memo.py:ParseMemo), which Parser.parse makes current while it runs. The model layer keeps there what it derives from the mutable models instead of on them: the dedup keys of a model, the member indexes of an enum (by model key), whether a field's type names its model (by field key) and the members a union node joined when it rendered (by node key). A value is kept with the epoch its owner has in its table; the methods that cleared the caches these memos replace (invalidate_render_caches, invalidate_semantic_caches) bump the epoch, so the memos return what those caches returned. Outside a parse values are computed at each read. DataModel.imports and the imports of a field are computed at each read; they keep no cache (DataModel.clear_imports_cache is a deprecated no-op). DATAMODEL_CODE_GENERATOR_CHECK_RENDER_MEMOS computes every returned value anew and fails on a difference, except for the dedup keys and self references whose stale values today's output keeps (legacy-stale-dedup-keys, legacy-stale-self-reference), which it records with a report file.

The mutation APIs are the GenerationStore methods listed in GENERATION_STORE_MUTATION_METHODS, for example replace_field_type, replace_nested_data_type, set_fields, set_base_classes, update_model_reference and redirect_reference_users. rename_model is the writer of class and reference names after the L2 settle; its callers apply six schemes (module, flattened module, field type, imported name, internal module and collapsed root), each with its own universe for uniqueness.

parser/_facts.py says which attribute holds which fact. ATTRIBUTE_FACTS has one row per owner class and attribute, __dict__ key, dict entry (extras["kw_only"]) or cached property, with its kind (fact, presentation, cache or bookkeeping), the Fact and RenderFact members a write changes, the store operations allowed to write it, the Phase whose passes write it last today and its freeze point: the latest freeze point among its facts (every Fact at B1, every RenderFact at its RENDER_FACT_FREEZE_POINTS entry), after which nothing may write it once the pass pipeline is in place. The finality checks still check each Fact at B1 unless a pass declares an exception. Bookkeeping rows name no fact and no store operation. The module docstring lists the three allowed exceptions to the kind rules (plan rows, rendered nullability, the schema-validator plan cache). The module imports only the standard library and typing_extensions (scripts/check_architecture_boundaries.py registers it as the facts leaf layer), so the checkers can read it without importing the package.

scripts/check_generation_store_usage.py (with tests/parser/test_generation_store_usage.py) reads that table and GENERATION_STORE_MUTATION_METHODS with ast and reports every write that does not go through a store operation:

  • in parser/: writes of fact and presentation attributes of model-graph classes (assignment, del, augmented assignment, setattr and object.__setattr__ with a literal name, item writes and list, dict and set mutators, also through a local alias), __dict__ writes, the direct .data_type, .fields, .base_classes and .reference writes, list mutators on model collections and Reference.children reads. A setattr with a computed name is reported too. Writes to the parser itself (self) and to schema objects (parameters annotated JsonSchemaObject, and the copies and SCHEMA_OBJECT_TYPE.model_validate results made from them) are not model writes;
  • in model/ and types.py: the same writes inside the parser-facing hooks (PARSER_HOOK_METHODS), the private helpers that write rendered state when a pass reads type_hint or collects imports (RENDER_STATE_WRITERS), and every model function these reach through calls on any receiver, at any depth, including writes to self. The closure stops at construction (CONSTRUCTION_METHODS), reference bookkeeping (REFERENCE_METHODS) and render entry points (RENDER_ENTRY_POINTS, each with its reason);
  • in all three: caches kept on model objects: __dict__ entries, cache attributes and cached_property.

Every finding is keyed by path, function and target, without line numbers, and scripts/generation_store_allowlist.toml holds the findings that existed when the checker learned them, with a count each. A new finding fails, and so does an entry that no longer matches, so the list only shrinks: a change that routes a write through the store removes its entry. The checker also fails when a model-graph class sets an attribute (in any method) without a row, when a row names nothing the sources declare or write, when a model method that parser code calls (directly, or by name through getattr/hasattr) reaches a fact write that no hook covers, and when a hook, construction or render-entry list names a function that no model module defines.

The checker does not follow these forms, so they must not be used for model writes: obj.__setattr__("name", value), obj.extras.__setitem__(key, value) and other dunder calls, unbound method calls such as list.append(obj.fields, field), and functools.partial(setattr, obj).

The runtime write guard (parser/_finality.py, DATAMODEL_CODE_GENERATOR_CHECK_STORE_WRITES) checks the same rule while the generator runs, for writes the scan cannot follow. Parser.parse arms it at the end of L1: DataType, DataModelFieldBase and DataModel get a __setattr__ guard for the fact and presentation attributes of ATTRIBUTE_FACTS, the lists those attributes hold become guarded copies (shared where the originals were shared; they are not list exactly and outlive the parse, acting as plain lists afterwards), each store operation named in a row's store_ops runs in a write scope, and the pipeline of parser/base.py opens pass scopes (pass_scope(name, phase): _build_module_structure in STRUCTURE, the plan segment in PLAN, each _process_single_module in MODULES, the cross_module and generic_base_class segments in CROSS_MODULE, the decide segment in DECIDE, the render_preparation segment, _finalize_modules included, in RENDER_PREPARATION, the finish segment in IMPORTS and the render segment in RENDER; before them, SETTLE; inert without an armed guard). A write outside every store operation is reported once per line and parse with the line that wrote it, the parser method running and the pass scope and phase; the construction of an object (its __init__ and what that calls) writes freely. Any store operation accepts any guarded write, and the phase is not checked: which operation and phase may write which attribute is left to the finality checks. With the area off nothing is installed. The guard does not see writes through object.__setattr__, through __dict__, into dict attributes, or into a list an object got outside a store operation after L1. The guards, the guarded lists and the store-operation scopes belong to the checks of one parse (parse_checks, armed by arm_parse_checks), which the finality check shares: they are installed when either area is on, and the guard reports writes only when STORE_WRITES is on, while the finality check uses them to learn which models a pass touched.

The test suite runs the guard in every test (tests/conftest.py:StoreWritesCheck): it reports into a file of the test process, and after each test the checker names each write of the package by the function that contains the reported line and by the target the scan gives that write (runtime_writes), and the test fails for a write the allowlist does not list. Most writes the guard sees are findings of the scan. A write only the guard sees (a method the hook closure does not reach, a write made inside a helper the scan stops at) has an entry whose value is its witness, the datamodel-codegen arguments of one run that makes it; python scripts/check_generation_store_usage.py --witnesses (and the test suite) run them, and an entry whose witness no longer writes it is stale. The entries only shrink, like the counted ones. When the scan learns to find a write a witness covers, the witness becomes a count entry (--write-allowlist makes that move); it is the only move that may raise the counted total.

Current behaviour that a decision reading the index must allow for:

  • Index queries answer over the parsed universe by default: the models parsers registered (Parser.results) plus redirected edges, removed ones included, not the module lists that L3–L6 edit. A model a later pass builds (a reuse subclass, the merged inherited Enum, the generic base class) is registered in the emitted universe only, and retire_model (replace_model for a model built in another's place) records each model that leaves the output (duplicates, reused and overridden models, unused models leaving their written module list). universe="emitted" answers over the models the output writes. Under DATAMODEL_CODE_GENERATOR_CHECK_MODEL_GRAPH, the written models must equal the emitted universe after render preparation, and with a report file each root-collapse decision on remaining references records when its answer over the emitted models differs (kind: universe-differs), the evidence for switching the default.
  • A store operation called with refresh="deferred" notes the models it changes for the next refresh but does not mark the facts dirty, so they stay as they were until another mutation. drop_union_member_constraints (msgspec unconstrain_union_members, slice assignment on data_types), swap_data_type for the nested lists of __replace_unique_list_to_set (which stay sets when an unhashable default keeps the field a list), apply_const (process_const() during collapse) and use_assignment_for_forward_references change models this way. Under DATAMODEL_CODE_GENERATOR_CHECK_MODEL_GRAPH, every refresh that records only the noted models compares its facts with a full rebuild.
  • The operations that write values the facts do not record neither note models nor mark the facts dirty: a field's default (set_field_default), required (require_field), constraints (set_field_constraints), extras (set_field_extras, set_field_extra, drop_field_discriminator), and the import of a model-level --type-overrides entry (override_type_import, add_model_import). An entry written into a field's extras, a discriminator dropped from a field's type and an override's import are seen by every holder of the dict or type. Writes on a copy that is not installed yet (_copy_resolved_inherited_field, _apply_override_to_field) stay outside the store.
  • Most fact writes after parsing still bypass the store; scripts/generation_store_allowlist.toml lists them by function. The checker cannot see writes through a model-list variable (models.sort() on a module's list), writes to module imports (ModuleContext.imports, which go through the import ledger and its runtime check instead, see L6 above), or writes in model methods that the hook closure does not reach; the runtime guard sees the last kind, and the allowlist lists them with a witness.
  • Dedup keys (cached on the model, read through ModelShapes.key) and model shapes are separate caches, not store facts.

Placement Guide¶

Procedure for a new decision:

  1. List every fact the decision reads, including facts of models reached through references, bases, variants and root models.
  2. Look up each fact in the finality table. Put the decision after the pass where the last of them becomes final. If that point is in L6, the decision is a cross-module pass, not a per-module one.
  3. If a pass that runs earlier needs the decision's result, move the pass that sets the fact earlier (for example, split it into a plan computed from facts that are final at that point and an apply step), or move the consumer after the decision. Never predict what a later pass will do.
  4. Before changing a node, check whether it can have more than one holder. Replace it in its owner through the store's mutation APIs instead of writing to it.

Scope on schema objects, not parse paths. When an option applies to part of a document, the walk that defines the part marks the schema objects in scope where the document is rewritten (L0), and L1 checks the mark on the object it parses. Parse paths are not document locations: legacy OpenAPI paths and parameters scopes, $ref merged with sibling keywords, $ref targets inside extension keys and properties whose names start with x- all produce paths that a path-based test misreads. The mark has to survive every step that builds a new object from a marked one: copy-on-write rewrites (_single_value_enum_as_const, _rewrite_schema_resource_refs), _validate_schema_object, _merge_ref_with_schema, synthetic enums, allOf and combined-schema merges, and OpenAPI operation copies. --use-single-value-enum-as-const has such a mark: its L0 walk marks every schema object that holds a const after the rewrite, written or rewritten, with x-datamodel-code-generator-read-as-const, and L1 _extract_const_enum_from_combined reads it as read_as_const. That it survives each of these steps is not verified. The schema location of Metadata Output is a mark of the same kind that each of these steps carries; the test suite checks with DATAMODEL_CODE_GENERATOR_CHECK_SCHEMA_LOCATIONS=1 only that every model has one at the end of L1, not that it is the right one.

Case Notes¶

  • #4834 (set and list models merged): L3 deduplication (__delete_duplicate_models with --collapse-reuse-models, __reuse_model_tree_scope) compares renderings in which unique-items arrays still read list, because __replace_unique_list_to_set runs later in L5. Dedup should compare a fact that is final at L1, the field's own unique-items intent, instead of the container. A container rule that also reads item hashability (item models, their fields, ClassVars and bases) can only be exact in L6, after __apply_generic_base_class and before __mark_set_item_models_hashable.
  • #4828 (default: {} that leaves out required fields): today __set_validate_default_on_fields decides per module in L5 that such a default is validated. The referenced model's required fields depend on discriminator tags (required literals, msgspec ClassVars), model-level type overrides and models of other modules, which are final only after the module loop. The decision is one L6 pass after __apply_generic_base_class that skips unused_models; constructor ordering then has to run again for the models whose defaults it drops, as __fix_tag_opt_out_field_ordering does for msgspec.
  • #4874 (scope of --use-single-value-enum-as-const): the L0 rewrite defined the scope, and the L1 decision in _parse_schema_obj (_extract_const_enum_from_combined turning a oneOf/anyOf of rewritten consts into a synthetic enum) needed it. The fix (#4926, #4927) put a mark on schema objects set by the L0 walk instead of testing the parse path.
  • #4873 (nullable one-value enums under --use-single-value-enum-as-const): the L1 const path does not carry nullable. _get_data_type returns _get_const_data_type before the strict_nullable and obj.nullable step, and process_const in DataModelFieldBase.__init__ decides nullability while the field is built (decide_literal_default, row legacy-const-drops-null). Until one pass after the L5 loop decides the nullability of const fields from where null comes from (nullable, type list, enum member, merging site), the L0 rewrite keeps a schema with nullable: true and a value other than null as an enum. Known limits until then:
  • _merge_ref_with_schema types a $ref with sibling keywords as a const when the site or the target was rewritten, and drops nullable from the other side: {$ref: P, nullable: true, maxLength: 5} and {$ref: P, nullable: true, enum: [p]} with P an enum of one value, and {$ref: N, enum: [n]} with N nullable, are typed Literal[...] without None, as a written const beside nullable is.
  • A nullable discriminator tag is typed as without the option (Literal['dog'] | None under --strict-nullable): pydantic models and pydantic dataclasses fail at import under --strict-nullable or --use-missing-sentinel, and msgspec leaves that variant untagged, so the union cannot decode it.
  • The rewrite reads only nullable: true; other values that JsonSchemaObject reads as true, such as "true", are rewritten and lose null.
  • _extract_const_enum_from_combined merges no branch of a oneOf/anyOf in which one branch keeps its enum, so the other one-value branches stay Literal[...] beside it (A | Literal['b']); msgspec cannot decode that union, nor the A | A1 it gets without the option.
  • #4496 (object maps): parse_pattern_properties grouped the patterns by the rendered hint of their value types (type_hint) at L1, before names, reuse and collapse are final, and returned a union of one dict per group, which rejects every object that mixes the groups and which msgspec cannot decode at all. Each map position built its dict on its own, so a type array lost its null at the root, in array items and in map values and lost its other types, and _get_data_type and _parse_nullable_map wrapped the dict of a type array of object and null in a union, where the property counts of a field no longer reach it. One builder (_parse_object_map) now builds every map from raw keywords of the map object, which are final at L1, and composes the value types without reading their renderings. One dict cannot give different keys different value types: where the patterns declare different value schemas, or the object admits keys that match no pattern, the builder warns once per schema location.
  • #4931 (property counts of validated pattern maps): parse_object built the root field of a dict root model from a copy of the object without patternProperties, so _get_property_count_constraints saw a closed object without patterns (max_length=0: every non-empty object rejected), and typed its keys str although propertyNames constrains them. Under --check-pattern-maps-strictly the field of a validated pattern map reads every keyword that counts keys from the object itself and takes its keys from propertyNames, the object models of the validators join the other types of a type array, and a pattern checks every declared key whose schema does not imply its own (_pattern_checks_declared_key); without it the 0.86.0 field, the object models without the other types and the 0.86.0 proof of a pattern that checks a declared key (_pattern_rejects_declared_value) are kept. The builder's key and null rules reach the field under --use-single-dict-for-object-maps.
  • #4835 (keys outside the patterns): parse_pattern_properties took no additionalProperties, so an open pattern map typed only the keys of its patterns and rejected every other key, although the schema types them by additionalProperties. The builder now hands it the keyword; a schema that asserts something admits the other keys and joins the value union, and an absent, true or empty one keeps the keys of the patterns.
  • #4803 (a const beside an enum): the L1 enum route was taken before the const was read, and only fields that write a const as Literal (process_const in DataModelFieldBase.__init__) narrowed the enum, so items, map values, union branches, msgspec fields and definitions kept every value. Both keywords are raw facts, final when the schema object reaches its route, so each route decides there: a value is typed as the const, and its enum class is still built as written, because users import it; a model built for the schema object itself is built from a copy that keeps the admitted values. A narrowed definition no longer deduplicates in L3 with an inline enum that lists every value, which then keeps a name of its own.
  • #4822 (missing Any import after collapse): same-module collapse shares the root type's data_types list between the root model and every site that inlined it. A later collapse that replaces a member calls set_nested_data_types on the member's parent (the root model's node), which rebinds only that node's list and detaches the old member; the other holders keep the emptied node. The index records shared nodes (shared_data_type_fact_ids) but not shared lists, so a pass that replaces such a node must find all its holders and replace it in each owner.
  • #4877 (msgspec layout conflicts): __flatten_conflicting_base_layouts flattens conflicting Structs in L4, because flattening changes field sets and bases that L5 reads (constructor ordering, discriminator tags, reuse). Whether to flatten depends on tags and reuse results that L5 and L6 produce, so it predicts them (__find_possible_tag_names, and __find_possible_reuse_duplicates, which compares type, bases and field names instead of renderings). A conflict that remains is rejected when the module is rendered (model/msgspec.py:Struct._validate_base_layouts through render_module_code, first in L6 _check_model_inheritance). Making those facts final earlier, as a discriminator tag plan and reuse groups computed before L5, lets flattening read plans instead of predictions.
  • --strip-default-none constructor order (Pydantic dataclasses, msgspec Structs): two readers answered "does the class body give this field a default?" differently. The Pydantic dataclass template keeps = None when the rendered type admits None, and msgspec Structs write UNSET or None for every optional field, while the constructor classifiers treated every stripped None default as no default, so a field without a default could follow one with a default. The L1 construction key reads only facts known when the model is built, and a None default that the option may keep counts as no default there, because rendered nullability is final only at L7. L5 __fix_constructor_field_ordering decides with the template rule (the assignment facts, through DataType.admits_none) and moves a kept None after the fields without a default, where the output stays valid whichever way the = None resolves at render. msgspec reads one predicate in both places, as a Struct never strips its defaults. Ordering decides from the field types and Field() arguments the class body renders, so a module applies --type-overrides to the field types of the models it keeps before __fix_constructor_field_ordering (#4949, #4955). Ordering runs after the decision phase for every module, so it reads a base in a module processed later with that module's overrides applied, too (#4914 step 3). A base class that an override replaces stays the generated model for ordering, as the generator cannot see the replacing class's fields: __apply_base_class_type_overrides keeps the generated model each replaced base stood for, and ordering reads it.

References And Names¶

ModelResolver is the naming and reference authority. It tracks the current root, base path, base URL, root IDs, and known references while parsers traverse documents. It also applies naming options such as aliases, model_name_map, prefixes, suffixes, duplicate suffixes, enum member normalization, and field name safety.

Reference.children still links references back to users, but newer parser post-processing should prefer GenerationIndex when it needs dependency facts. The index records live models and avoids depending on legacy side effects alone.

Output Backends¶

Parsers do not hard-code Pydantic, dataclass, TypedDict, or msgspec classes. get_data_model_types() returns a DataModelSet for the selected DataModelType. That set injects:

  • the model class
  • the root model or type alias class
  • the field class
  • the type manager
  • optional reference dumping behavior
  • GraphQL scalar and union model classes

The same parser output can therefore render into different Python model styles while sharing the same reference and module-generation pipeline.

Layer Dependency Rules¶

The pipeline is also a dependency boundary. Configuration and entry points select behavior, parsers normalize source formats, and output models own rendering-framework behavior. Keep these rules when adding features or optimizing hot paths:

  • Parser modules may depend on neutral DataModel, DataModelFieldBase, and declared capability hooks. They must not import or identify concrete Pydantic, dataclass, TypedDict, or msgspec output implementations.
  • Output-specific constructor, forward-reference, runtime-validation, import-conflict, and rendering behavior belongs to the output model that implements it. The parser calls the neutral capability without switching on backend names. This includes annotation representation, TypedDict provider selection, configuration assembly, and access to prepared output metadata. Existing custom-template keys and extension capabilities remain compatibility contracts; moving their preparation between layers must preserve generated code, insertion order, and option precedence.
  • Output models inject reserved-field and generated-import conflict handling through FIELD_NAME_RESOLVER_CLASS; ModelResolver owns only neutral normalization and lazily creates the selected resolver. Legacy resolver imports and default ModelResolver policies resolve those output-owned providers lazily.
  • Reusable graph, detection, enum, cache, JSON Schema reference rewriting, and parser retry-signal helpers belong in neutral package modules. Code outside parser/ must not import private parser modules or private symbols from public parser modules, such as parser.mcp._rewrite_schema_refs.
  • Input-model conversion reads output-family compatibility from the output selection registry. It must not maintain a second DataModelType-to-backend mapping.
  • Input-model build tokens must resolve to neutral input_model_result schema annotations before parser construction. Parsers consume that IR and must not import the private input-model transport. The former token table and parser factory remain lazy private compatibility paths and are not allocated by normal generation.
  • Configuration must not acquire new parser or concrete output-backend dependencies. Historical concrete defaults are narrowly allowlisted until they can be migrated without changing the public ParserConfig surface.
  • Entry points project source and reference settings into a frozen ParserSourceContext attached to their lightweight, already-validated config; direct parser APIs retain typed configuration and validation.
  • What generated code requires of its target is one frozen table in _requirements.py: each construct's library and minimum version, what an unset Pydantic target means for it, and the typing_extensions backport an older Python target imports. The version gates of the parsers and the model backends, PythonVersion.has_*, the StrEnum gates of presets and the CLI, the Pydantic checks of server and client targets, and the backport import constants read it instead of comparing versions. Not yet rows: the Pydantic target that base_config.implied_target_settings implies for server and client targets, the Python minimum of _api_generation, the PEP 695 placeholder check of the built-in formatter, and the per-version type backports of _python_type_import_registry.
  • Which constraint keywords each type takes is one static table in _constraint_applicability.py (see One home per decision): the public tables of DataTypeManager and its Pydantic and msgspec subclasses, and the keyword groups types.py exports, are views of its rows.

Run python scripts/check_architecture_boundaries.py to validate these rules. The checker parses imports and semantic backend inspection with the Python AST, including lazy and dynamic imports. Entrypoint, parser, configuration, input-model, reference, model-composition, output-model, shared-model, schema graph, parser pass, requirement-table, constraint-table, and debug check flag files are classified explicitly. The composition root may select concrete backends, while shared-model modules must remain neutral: they cannot import a concrete backend or resolve one through sys.modules, including module-name constants and aliases. The requirement table may import only the standard library, typing_extensions and enums, the constraint table only those and the requirement table, _checks.py, which every layer reads for the debug check flags, only the standard library and typing_extensions, and the schema graph (parser/_schema_graph.py, L0) only those and reference: the parsers pass it their rules. Pass modules (parser/_passes/) follow the parser rules and import no parser module but the generation store, the import ledger, _python_type_imports and each other, not even for typing: a helper that passes of more than one layer call is a function there (parser/_passes/_shared.py) that takes parser state as arguments or through a narrow Protocol, so it never imports parser/base.py. This keeps backend-specific lifecycle and cache ownership with the backend or composition root, without blocking neutral module registry access such as sys.modules[model_type.__module__]. Private parser lifecycle access and reference-owned backend policy therefore cannot hide in the shared layer. Its legacy allowlist is keyed by file, enclosing symbol, rule, and target; extra occurrences fail, and removed dependencies make stale entries fail so the exception cannot silently become permanent. The same check runs in pre-commit and pytest with actionable diagnostics.

Rendering And Formatting¶

Every DataModel renders through a Jinja2 template. Built-in templates live in src/datamodel_code_generator/model/template. A custom template directory can override a built-in template by path.

Imports are collected separately from rendering through Import and Imports. The import layer handles grouping, aliases, reference-bound imports, future imports, unused import removal, and __all__ generation.

CodeFormatter then applies the configured formatter pipeline. The formatter layer supports the built-in formatter, black, isort, ruff check, ruff format, and user-supplied custom formatters.

Metadata Output¶

When --emit-model-metadata is enabled, Parser.parse() describes each generated model by the location of the schema object it is built from. generate() then serializes the resulting payload through model_metadata.py. The JSON Schema for that payload is stored in src/datamodel_code_generator/resources/model_metadata.schema.json and exposed through --output-format-json-schema model-metadata.

source_ref is the document as reference paths name it, #, and the RFC 6901 JSON Pointer of the schema object from that document's root (~ as ~0, / as ~1, no percent-encoding): a JSON Pointer string, not a URI fragment, never relative to an $id and never a parse path. source_path holds the decoded tokens. Several models can share one location (read and write variants of one schema, models copied through a $ref, a combined class and its branch), so module and class_name identify a model. Converted inputs (Avro, XML Schema, Protocol Buffers, payloads AsyncAPI converts) point into the converted JSON Schema; a converted AsyncAPI payload is located at the payload it comes from. GraphQL has no JSON document, so its models keep their reference paths, as does a model that a custom parser builds from a copy of a schema object.

The location is a fact recorded in L0 and L1:

  • L0. _index_document makes each loaded document a tree and indexes every JSON container of it by identity in the location table of the schema graph (parser/_schema_graph.py:SchemaGraphBuilder.index_document). A container met at a second position (a PyYAML alias, an object an API dict input shares, a mirror file served for several URLs) is copied for that position and its holders copy on write, so the location does not depend on the YAML loader or the caller; a container that is its own ancestor keeps a back edge to its copy. AsyncAPI indexes its document at load, and a converted payload schema is mounted at the payload's location (_mount_converted_schema).
  • Carrier. JsonSchemaObject.schema_location lives in the object's __dict__, not in its fields. The object takes it from the document object or located dump (_LocatedDict) it is validated from, through the schema graph that Parser.parse publishes in a ContextVar (SCHEMA_GRAPH): _located_model_schema (the model's __get_pydantic_core_schema__) wraps the field validation inside the model schema, so every validation of the model locates it, in any field, a subclass's own included, and through TypeAdapter. MediaObject takes its location the same way. A model validator in wrap mode would rename the model in pydantic's error locations (function-wrap[...] instead of JsonSchemaObject). During a parse, model_dump returns located dumps whose schema children remember their own sources. An object a copy step builds stands for one source object by rule: the use site of a $ref with siblings, the union branch, the allOf holder, the holder of a synthetic enum or of an itemSchema array, or the member property it normalizes. A dict a merge helper builds from two sources takes the location of the side the helper lets win. A boolean schema, which cannot carry a location, takes it from its holder.
  • Copy steps the location survives, besides those under "Scope on schema objects": L0 unsharing, openapi.py:RawMediaObject (the media object's own schema value is used), lists joined and dicts merged in _deep_merge, _merge_all_of_schema, _merge_property_schemas and _merge_inherited_type_shape_dict (and the nested schemas intersect_keywords rewrites in their result, copied with the location they had there), combined classes in _parse_object_common_part, inherited normalizations in _merge_properties_with_parent_constraints, array type-union branches, OpenAPI operation copies for path-level parameters and global security (the operation's location is passed as an argument), the dangling-reference fallback (located at the missing target), and converted AsyncAPI payloads.
  • L1. _record_schema_object(reference, obj) stores the location and the frames of the models being built on the Reference object, so later changes of Reference.path (L3 _internal modules, L5 collapse renames) do not lose it. The operation parameters model takes the operation's location; read and write variants take the base schema's. location_of(reference) reads it. When two different schema objects reach one Reference because their parse paths collide (the anyOf branches of several allOf members, #4853), either location could disagree with the model's content, so the Reference keeps none and is marked as conflicting, and so does the class built for an allOf union member from such a Reference; their metadata keeps the reference path, as a model without a location does.

With DATAMODEL_CODE_GENERATOR_CHECK_SCHEMA_LOCATIONS=1, which tests/conftest.py sets for the test suite, a parse of a JSON document raises at the end of L1 when a model has no location and is not marked as conflicting, so a copy step that loses a location fails in CI. The check sees only whether a location is present, not whether it is right. The recommender (_recommend/_metrics.py) matches classes by their internal identity paths, passed beside the metadata and never written, and describes their locations from the JSON Pointer tokens.

Messages name the same location, as document#pointer with the document URL redacted: the SchemaParseError that _validate_schema_object raises for a schema value it cannot read, the unsatisfiable-schema errors (_raise_unsatisfiable_schema takes the schema whose allOf or anyOf leaves no value), the Schema path: warnings of --schema-version-mode strict, and "A Parser can not resolve classes" (location_of of each model). A value that is not a JSON object (a boolean schema, or a scalar where a schema belongs) takes the location of its holder from the code that reads it there (_validate_member, _parse_raw_at). Where no location is known (a copy a custom parser validates, a GraphQL model), a message keeps the parse path or reference it printed before.

Runtime Dynamic Models¶

generate_dynamic_models() uses the normal generate() API to produce code, executes that code in temporary modules, and returns real Pydantic v2 model classes. Multi-module output is topologically sorted by relative imports before execution. The result is cached by schema and config hash when caching is enabled.

Performance-Sensitive Paths¶

Recent work has focused on reducing work without changing the generation model:

  • fast CLI paths avoid importing heavy modules
  • format.py keeps format-related types in a lighter helper module
  • local schema sources are reused during $ref resolution
  • YAML unsupported-tag scanning is skipped when no unsupported tag marker is present
  • JSON Schema constraint extraction avoids dumping whole schema objects when only selected constraint keys are needed
  • simple field import collection avoids rendering a full type hint when DataType facts are sufficient

These optimizations keep the architecture stable: parsers still build the same graph, and renderers still produce the same code, but hot paths do less incidental work.
