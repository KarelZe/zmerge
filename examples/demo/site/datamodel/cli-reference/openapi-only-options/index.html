--dedupe-request-response-variants¶

Decide Request/Response variants from the schema graph and build each inline model once.

Under --read-only-write-only-model-type (request-response or all), the generator decides which models split into Request and Response variants. Without the flag it decides as 0.86.0 did, from a temporary parse of each referenced schema; that parse takes class names and can emit unreferenced copies, so other classes get higher numbers (Child1Request where ChildRequest is free), and a schema whose parse reaches itself again through the models it builds stops there. A child that inherits from an allOf parent also builds the inline models of the parent's properties a second time (Payload1 unused, Payload2 referenced). Some recursive schemas cannot be generated that way and the error names this flag.

With the flag the decision reads the raw schemas only: an input without readOnly or writeOnly gives the models it gives without --read-only-write-only-model-type, and each inline model is written once (Payload1 referenced). Both forms validate the same data.

Usage

datamodel-codegen --input read_only_write_only_allof_parent_inline_models.yaml --output-model-type pydantic_v2.BaseModel --read-only-write-only-model-type request-response --dedupe-request-response-variants # (1)!
  1. --dedupe-request-response-variants - the option documented here
Examples

Input Schema:

openapi: 3.1.0
info:
  title: t
  version: '1'
paths: {}
components:
  schemas:
    Child:
      allOf:
        - $ref: '#/components/schemas/Parent'
        - type: object
          properties:
            payload:
              properties:
                extra:
                  type: string
    Parent:
      type: object
      properties:
        id:
          type: integer
          readOnly: true
        payload:
          type: object
          properties:
            value:
              type: object
              properties:
                code:
                  type: integer

--include-path-parameters¶

Include OpenAPI path parameters in generated parameter models.

The --include-path-parameters flag adds path parameters (like /users/{userId}) to the generated request parameter models. By default, only query parameters are included. Use this with --openapi-scopes parameters to generate parameter models that include both path and query parameters.

See also: OpenAPI Options

--openapi-paths-bodies-as-definitions¶

Give the bodies of the paths and webhooks scopes the models their schema definitions get.

With --openapi-scopes paths (or webhooks), request and response bodies are parsed by their own dispatch, which types some object bodies inline although a schema definition of the same body gets a model: a body whose type array admits objects, such as type: [object, "null"], or one with additionalProperties, patternProperties or propertyNames and no type. With --openapi-paths-bodies-as-definitions, such a body gets the model its definition would get, such as a root model of dict[str, Any] | None, whose values --use-typed-nullable-map-values types as declared. A document whose only bodies are such schemas then generates models instead of failing with "Models not found in the input data", whose message names this option when it applies. Bodies typed as objects, arrays, combinations, enums and references, and the api scope, are unchanged.

Usage

datamodel-codegen --input type_array_request_body.yaml --openapi-scopes paths --openapi-paths-bodies-as-definitions # (1)!
  1. --openapi-paths-bodies-as-definitions - the option documented here

              type: [object, "null"]

--read-only-write-only-model-type¶

Generate separate request and response models for readOnly/writeOnly fields.

The --read-only-write-only-model-type option controls how models with readOnly or writeOnly properties are generated.
